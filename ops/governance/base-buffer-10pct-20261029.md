# Base: резерв 10% без фиксированного минимума — только подготовка

Статус на 2026-10-29: **не подписано, не поставлено в очередь, не исполнено**.
Публичный план: [base-buffer-10pct-20261029.json](base-buffer-10pct-20261029.json).
В нём нет ключей, nonce, подписей или команд перемещения средств.

## Что меняется

Единственное изменение — `minimumBuffer: 5000000 → 0`. Порядок и все остальные
значения `EpochVault.Limits` сохранены из сети, а не взяты из настроек реестра.

| Поле | Сейчас | После исполнения |
| --- | --- | --- |
| minDeposit | 1 USDC | 1 USDC |
| maxEpochDeposits | 500 USDC | 500 USDC |
| minimumBuffer | 5 USDC | 0 USDC |
| minBufferRatio | 10% | 10% |
| maxInstantWithdrawal | 25 USDC | 25 USDC |
| dailyInstantLimit | 50 USDC | 50 USDC |
| instantFee | 0,25% | 0,25% |
| instantMaxTickAge | 7200 с | 7200 с |

Формула контракта станет `10% × последний принятый navBid`, с округлением вниз
до минимальной единицы USDC. Это минимальный ликвидный резерв, а не автоматическая
аллокация. После исполнения деньги останутся в хабе до отдельного размещения.
Около 90% утилизации возможно после размещения свободного остатка, если нет
дополнительных потребностей в ликвидности. При меньшем резерве доступная ликвидность
для мгновенных выводов уменьшается; номинальные лимиты выводов не гарантируют
наличия всей этой суммы в хабе.

Режим allocator `propose`, работа операторов, реестр deployment-параметров, старые
таймеры и почасовое обновление мониторинга этой подготовкой не изменены.

## Проверка и подписание владельцем

Перед **каждой** подписью выполнить только читающую проверку:

```bash
cd /root/optimized-rebalancer-contracts/ops
node --require ts-node/register/transpile-only src/prepare-buffer-10pct.ts \
  check governance/base-buffer-10pct-20261029.json
```

1. При `ready_to_queue` проверить содержимое `transactions.queue` в JSON и
   подписать/отправить **только этот** запрос своим кошельком. Адрес `to` — Timelock,
   а не vault или strategy. Кошелёк выбирает актуальные nonce и газ. Если owner
   параллельно используется оператором, сначала согласовать nonce/окно отправки;
   этот инструмент операторов не останавливает и nonce не резервирует.
2. Дождаться подтверждения queue. Проверка должна показать `queued_waiting`.
   **Не объединять queue и execute в одну пачку.** Сохранить исходный JSON и hash
   queue-транзакции; не менять ETA, calldata или ID уже поставленного плана.
3. После ETA снова выполнить проверку. Только при `ready_to_execute` и успешном
   `eth_call` для `execute` проверить и подписать `transactions.execute`. После
   подтверждения проверка должна показать `target_already_applied`.

При ошибке проверки, изменении любого лимита, владельца, задержки или кода
контракта **не подписывать**. Проверка — снимок состояния: она не блокирует другие
governance-транзакции между проверкой и включением в блок. `setLimits` переписывает
весь кортеж и не содержит compare-and-swap, поэтому повторная проверка и отсутствие
конкурирующих изменений обязательны.

`targetCalldata` в JSON — данные внутреннего вызова для проверки, **не отдельная
транзакция владельца**. Только Timelock вправе вызвать `setLimits` у vault.

Если окно queue пропущено и операция **не была поставлена**, создать новый файл
с новой ETA, проверить и заново согласовать его; не редактировать старый план:

```bash
node --require ts-node/register/transpile-only src/prepare-buffer-10pct.ts \
  prepare governance/base-buffer-10pct-next.json
```

Если старый план уже в очереди, сохранить именно его и использовать `check`;
нельзя подменять его свежесгенерированным execute. Если параметры изменились,
дальнейшие действия, включая отмену, требуют отдельного решения владельца.

Утилита поддерживает только `prepare` и `check`. RPC по умолчанию публичный
`https://mainnet.base.org`; при необходимости можно задать `BUFFER_READ_RPC_URL`
без внесения URL/ключа в JSON или git. Импортов operational config, загрузки
секретов, signer и отправки транзакций нет. RPC ограничен разрешёнными читающими
методами. Существующий файл никогда не перезаписывается.
