# ТЗ: кросс-чейн аллокатор капитала для Thesauros

Версия 1.0, 2026-09-28. Исполнитель — бекенд-разработчик Thesauros-Rebalance-Engine.

Контракты и сервисы, на которых строится работа, лежат в `optimized-rebalancer-contracts`, ветка `feat/crosschain-tick-epoch`.

---

## 1. Задача одним абзацем

Нужен сервис, который решает, где держать капитал кросс-чейн ваулта: сколько на Base, сколько на Arbitrum, в каких провайдерах (Aave, Compound, Morpho). Сервис исполняет решение разрешёнными вызовами контрактов. При этом он в первую очередь обеспечивает ликвидность для выплат пользователям.

Всё остальное уже работает и в задачу не входит:

- учёт и NAV (тики);
- эпохи, клиринг и клеймы;
- доставка CCTP-переводов;
- мониторинг;
- индексер.

Без аллокатора система безопасна, но деньги лежат в буфере ваулта и почти ничего не зарабатывают.

## 2. Как устроена система (минимум, который нужно понимать)

```
Base (хаб)                                   Arbitrum (спок)
┌──────────────────────────────┐             ┌─────────────────────────┐
│ EpochVault  (доли, очередь,  │             │                         │
│   буфер наличности)          │             │                         │
│      │ pushToAgent ▲ returnToVault          │                         │
│      ▼             │         │   CCTP V2   │                         │
│ ChainAgent (Base) ─┼─bridgeOut────────────► │ ChainAgent (Arbitrum)   │
│      │ allocate / deallocate ◄───bridgeOut─ │      │ allocate/deallocate│
│      ▼                       │             │      ▼                  │
│ Rebalancer-стратегия         │             │ Rebalancer-стратегия    │
│  (Aave, Compound, 3×Morpho)  │             │  (Aave, Compound, 3×Morpho)
└──────────────────────────────┘             └─────────────────────────┘
 TickAccountant: NAV-тики (сервис nav)   relayer доставляет переводы
 keeper: эпохи/клиринг/фондирование      monitor, indexer + API
```

- **Пользователи.** Они ставят заявки на депозит и вывод в `EpochVault`. Заявки исполняются пачкой в конце эпохи (раз в 4–6 часов). Выводы оплачиваются из **наличности ваулта на Base**. Если её не хватает, выплата ждёт.
- **Капитал в работе** лежит в стратегиях (`Rebalancer`) на каждой сети. Держатель долей стратегии — `ChainAgent` этой сети.
- **Перемещение между сетями** идёт только через `ChainAgent.bridgeOut` по заранее заданным маршрутам. Доставку делает сервис `relayer`. Время стандартного CCTP-перевода нужно замерить на стенде (ориентир — десятки минут: Circle ждёт финальности исходной сети).
- **Исполнитель** (EXECUTOR_ROLE) — единственная роль, которая двигает деньги. Её ключ и будет у аллокатора.

Подробности: `docs/tick-accounting-design.md`, `docs/crosschain-deployment.md` (раздел 5 «Operations»), `docs/crosschain-limits.md`.

## 3. Что есть в Rebalance-Engine сейчас и что переиспользуем

По результату разбора кода `apps/rebalancer`:

| Есть | Переиспользуем? |
|---|---|
| Независимые циклы: одна сеть, один ваулт; режимы `Propose` / `Approve` / `Execute` / `Backtest` | Каркас модулей, cron и логику режимов — да. Нужен **новый режим** `CrossChain` с общим решением по всем сетям |
| Оптимизатор: жадное заполнение по текущей ставке с общим процентным лимитом на провайдера; ставка не зависит от размера депозита; газ не учитывается | Как отправная точка — да. Нужно расширение (раздел 4.2) |
| RiskGuard: аномалии ставок, cooldown, circuit breaker по `totalAssets` (Redis) | Да, в том же виде, для каждой стратегии |
| Отправка транзакций с EOA (`Approve`), ключ из AWS Secrets Manager (`resolvePrivateKey`) | Да, тот же механизм для ключа EXECUTOR |
| Реестр сетей `libs/networks`, `multicall`, провайдеры RPC | Да. Добавить адреса кросс-чейн контрактов из манифестов `deployments/<net>/crosschain.json` |
| AlertManager / Telegram | Да |
| Backtest через форк hardhat | Частично: каркас «форк на блоке». Сейчас он односетевой, симуляция ликвидности не работает (выставляет ETH, а не токен) |
| HTTP health | **Нет.** Нужно добавить `/health`, чтобы его видел healthchecker |

## 4. Функциональные требования

### 4.1 Входные данные (снимок состояния на каждой итерации)

Всё читается с сетей через multicall или из API индексера (`GET /v1/vault`, `/v1/allocation`, `/v1/transfers`).

| Данные | Источник |
|---|---|
| Наличность ваулта: `cash`, `pendingDeposits`, `liabilities`, `reserved`, `freeCash`, `minimumBuffer()` | `EpochVault.accounting()`, `freeCash()`, `minimumBuffer()` |
| Неоплаченные выводы и их возраст | `cursors()`, `getEpoch(nextFund)` |
| Прогноз оттока | Доли в эскроу текущей эпохи × `rateBid`, плюс остаток дневного лимита мгновенных выводов (`/v1/vault` → `limits.instantRemainingEstimate`) |
| Прогноз притока | `pendingDeposits` (станут наличностью после клиринга) |
| По каждой сети: `idle` агента, доли стратегии, стоимость | `ChainAgent.idle()`, `strategyShares()`, `Rebalancer.convertToAssets` |
| По каждому провайдеру: баланс, ставка, лимит, здоровье | `getDepositBalance`, `getDepositRate`, `getProviderCap`, `providersHealthy()` |
| Ликвидность рынка (сколько можно реально вывести сейчас) | Aave: `availableLiquidity` резерва; Compound: `totalSupply − totalBorrow`; MetaMorpho: `maxWithdraw` ваулта |
| Переводы в пути | `/v1/transfers` (state = `in_flight`) |
| Ограничения маршрутов | `ChainAgent.getRoute(routeId)`: `maxPerTransfer`, `capacity`, `level`, `refillPerSecond`, `enabled` |
| Предохранители | `TickAccountant.frozen()`, `bridgeSendsAllowed()`, `chainSendAllowed(dstChainId)`, `maxChainExposure()`, `isChainOverExposed(chainId)`, флаги последнего тика; `EpochVault.paused(5)`; `ChainAgent.paused(0/1)` |

### 4.2 Решение: целевое распределение

Цель — максимизировать ожидаемый доход портфеля за горизонт H (параметр, по умолчанию 7 дней) за вычетом издержек:

```
max Σ_chain Σ_provider  x[c,p] · apr[c,p](x) · H  −  Σ_moves cost(move)
```

- **`apr[c,p](x)` — ставка с учётом влияния собственного депозита.** Для Aave и Compound это модель ставки от utilization с параметрами из контракта рынка. Для MetaMorpho допустима линейная аппроксимация по ставкам рынков в withdraw queue. Первая версия может брать текущую ставку, но с жёстким потолком доли в рынке (параметр `maxShareOfMarketBps`). Это обязательно, чтобы не «продавить» ставку своими деньгами.
- **`cost(move)` включает:**
  - газ на каждой сети (оценка `estimateGas` × текущая цена);
  - комиссию CCTP по котировке Circle (запрашивать перед каждым переводом; `minReceive` ставить не выше суммы за вычетом комиссии);
  - **альтернативную стоимость** денег в пути: сумма × apr × время доставки;
  - для межсетевых перемещений — `maxTransit` из конфига, до получения реальной статистики.
- **Гистерезис.** Перемещение делается только если выигрыш за H больше `cost × K`, где K — параметр (по умолчанию 2), и больше `minMoveUsd`.

### 4.3 Жёсткие ограничения (нарушать нельзя; контракт иначе отклонит транзакцию или поднимет флаг)

1. **Буфер.** `pushToAgent` можно делать только если после него `freeCash − неоплаченные выводы ≥ minimumBuffer()`.
2. **Лимиты провайдеров** в стратегии, в bps от её активов.
   - Любой `allocate` попадает во входного провайдера (Aave, без лимита). Затем распределение делается `Rebalancer.rebalance` с учётом лимитов.
   - Ребаланс, который превышает лимит, откатится.
3. **Маршруты:** `amount ≤ maxPerTransfer`, `amount ≤ текущий уровень ведра`, `minReceive ≥ amount × (1 − maxFeeBps)`.
4. **Деньги в пути не больше `maxInFlightRatio` от NAV** (25% в боевом профиле). Если лимит превышен, тик получит флаг, и отправки с хаба остановятся до доставки.
5. **Концентрация по сетям.** `TickAccountant.maxChainExposure()` задаёт потолок доли одной сети в признанном NAV (0 = выключено). Превышение ставит на тик флаг `FLAG_CHAIN_EXPOSURE` и помечает конкретную сеть: `chainSendAllowed(dstChainId)` вернёт false именно для неё. Важно для планировщика: блокируется отправка **в** переполненную сеть, а не **из** неё, поэтому corrective-перевод избытка наружу всегда разрешён. Перед выбором направления читать `chainSendAllowed`, а не только глобальный `bridgeSendsAllowed`.
6. **Предохранители:**
   - при `frozen()` или `!chainSendAllowed(dst)` — никаких `bridgeOut` в эту сеть и никакого `allocate` на хабе;
   - на паузе — никаких вызовов соответствующего домена;
   - `deallocate`, `deallocateShares` и `returnToVault` разрешены всегда.
7. **Нездоровые рынки.** Если `providersHealthy() == false`, в эту стратегию не аллоцировать: депозиты в неё будут отклонены.

### 4.4 Ликвидность для выплат (приоритет выше доходности)

Порядок работы на каждой итерации:

1. **Покрыть неоплаченные выводы** (`liabilities − reserved > 0`). Источники берутся по возрастанию времени доступности:
   - `idle` хаб-агента → `returnToVault`;
   - хаб-стратегия → `deallocate` → `returnToVault`;
   - споки → `deallocate` → `bridgeOut` на хаб → после доставки `returnToVault`.

   Keeper умеет только первые два источника (`KEEPER_AUTOFUND`). Аллокатор должен уметь все три.
2. **Держать целевой буфер:** `targetBuffer = max(minimumBuffer(), прогноз оттока до конца следующей эпохи × safetyFactor)`, по умолчанию `safetyFactor = 1.5`. Излишек сверх `targetBuffer + hysteresis` уходит в работу.
3. **SLA:** выводы должны быть профинансированы не позже чем через `fundingSlaHours` после клиринга (параметр, по умолчанию 12 ч). Если по расчёту SLA не выполняется (капитал заперт в рынке без ликвидности), нужен немедленный алерт с суммой и причиной.

### 4.5 Исполнение: план → шаги → состояние

**Разрешённые вызовы.** Использовать только эти функции, ничего сверх:

| Контракт | Функции |
|---|---|
| `EpochVault` (Base) | `pushToAgent(assets)` |
| `ChainAgent` (каждая сеть) | `allocate(assets)`, `deallocate(assets)`, `deallocateShares(shares, minAssets)`, `bridgeOut(routeId, amount, minReceive, rebalanceId)`, `returnToVault(assets)` (только хаб) |
| `Rebalancer` (стратегия каждой сети) | `rebalance(amounts[], sources[], destinations[])` |

- **routeId:** `keccak256("thesauros.route.v1:<srcChainId>-><dstChainId>")`.
- **rebalanceId:** уникальный id плана (bytes32). Он пишется в событие `BridgeOut` и нужен для сквозной трассировки.
- **minAssets** в `deallocateShares(shares, minAssets)` — пол, ниже которого выкуп доли стратегии откатится с `SlippageExceeded`. Считать из `strategy.convertToAssets(shares)` с небольшим допуском вниз: количество полученного всё равно измеряется по факту баланса, но план должен падать сразу, а не узнавать о проскальзывании только на следующем тике. Для `deallocate(assets)` пол не нужен — там количество фиксируется точно.

**План** — это последовательность шагов с зависимостями, например:

```
deallocate(Arbitrum, 40k) → bridgeOut(Arbitrum→Base, 40k) → [ждать BridgeIn] → returnToVault(Base, 40k)
```

**Состояние плана и шагов** хранится в Postgres (новая таблица), чтобы после рестарта продолжать, а не повторять:

```
PLANNED → STEP_SENT(txHash) → STEP_CONFIRMED → … → AWAITING_DELIVERY(transferId) → DELIVERED → DONE
                                  └──────────────→ FAILED(reason) / ABANDONED
```

Правила исполнения:

- **Симуляция.** Каждый шаг перед отправкой проверяется через `eth_call` (`staticCall`). Если он откатился, не отправлять, записать причину и пересчитать план.
- **Одна транзакция за раз** на ключ и сеть, с управлением nonce.
- **Идемпотентность:**
  - шаг `bridgeOut` считается выполненным, если в сети есть событие `BridgeOut` с этим `rebalanceId`;
  - доставка засчитывается по событию `BridgeIn` с тем же `transferId`.
- **Таймауты.** Если перевод не доставлен за `maxTransit` — алерт. Если не доставлен за 4 × `maxTransit` — критический алерт.
- **Параллельные планы.** Не начинать новый межсетевой план, пока не завершён предыдущий. Исключение — перемещения внутри одной сети.

### 4.6 Режимы работы

| Режим | Поведение |
|---|---|
| `Propose` | Считает план, пишет его в лог и Telegram, ничего не отправляет |
| `Approve` | Считает и исполняет |
| `Stand` | То же, что `Approve`, но с потолком суммы на операцию (`standMaxMoveUsd`) и более частыми итерациями. Для тестового стенда на 50–100 долларов |

Итерация запускается раз в 15 минут и дополнительно сразу после событий `RedeemsCleared` и `BridgeIn`. Cooldown между межсетевыми планами — параметр `crossChainCooldownMinutes`, по умолчанию 60.

## 5. Нефункциональные требования

- **Ключи.** Ключ EXECUTOR хранится в AWS Secrets Manager через существующий `resolvePrivateKey`. В env его быть не должно. Сервис не получает никаких других ключей.
- **Health.** HTTP `/health` отвечает 200 или 503. 503 — если последняя итерация была больше 30 минут назад, есть план в `FAILED` без разбора, или есть неоплаченные выводы сверх SLA. Endpoint добавить в `HEALTHCHECK_URLS`.
- **Метрики.** Нужны доля капитала по сетям и провайдерам, средневзвешенный APR, объём в пути, время финансирования выводов, число шагов по статусам. Формат — Prometheus `/metrics` или Redis + лог, как сейчас.
- **Алерты** в Telegram через AlertManager:
  - план исполнен или провален;
  - SLA выплат под угрозой;
  - превышение лимитов по результату пересчёта;
  - аномалия ставки (существующий RiskGuard).
- **Конфигурация** — env плюс реестр сетей. Адреса берутся из манифестов, а не хардкодом. Добавление сети не требует кода, только конфиг.
- **Логи:** JSON, без секретов (существующий `telegram-logger` умеет редактировать).

## 6. Тестирование и приёмка

**Тесты:**

1. **Unit.** Оптимизатор на синтетических входах, свойства проверяются генеративно:
   - никогда не превышаются лимиты провайдеров и маршрутов;
   - не превышается `maxInFlightRatio`;
   - буфер не уходит ниже минимума;
   - при `frozen` — пустой план (кроме шагов фондирования).
2. **Интеграция на форках.** Взять стенд из `optimized-rebalancer-contracts/ops/rehearsal/run.sh`: два anvil-форка, полный деплой, локальный аттестатор CCTP, живые сервисы nav, keeper и relayer. Прогнать сценарии:
   - (а) депозит 200k: аллокатор разводит капитал по сетям и провайдерам в пределах лимитов;
   - (б) вывод 50% TVL: выплата профинансирована со спока в пределах SLA;
   - (в) рестарт посреди плана: план продолжается, повторов нет;
   - (г) `freeze()`: новые отправки прекращаются, фондирование продолжается;
   - (д) провайдер с отказавшим view: аллокации в него нет.
3. **Backtest.** Сравнить доходность с «всё в лучшем провайдере хаба» на исторических ставках за 90 дней с учётом газа.

**Критерии приёмки:**

- все пять сценариев на форках проходят автоматически в CI;
- ни одна транзакция аллокатора на форках не откатывается из-за нарушения ограничений раздела 4.3;
- на стенде (50–100 USD) аллокатор проработал 72 часа без ручного вмешательства, мониторинг без критических алертов.

## 8. Открытые вопросы (решить до этапа 3)

1. Горизонт H и коэффициент гистерезиса K — продуктовое решение: чаще двигать ради доходности или реже ради газа.
2. Разрешены ли быстрые CCTP-переводы (платные, по котировке Circle, быстрее стандартных) для срочного фондирования выводов?
3. Нужен ли глобальный потолок на протокол по всем сетям (например, Aave суммарно не больше 60%)? Сейчас лимиты есть только внутри стратегии каждой сети.
